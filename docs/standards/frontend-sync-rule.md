# FlowGate 前端与业务同步规范（V1 产品化优先）

> 2026-11-05 确认；**2026-11-06 新要求：V1必须有正式产品后台**。旧测试台依旧保留；当前产品化合同以 `docs/design/product-console-v1.md` 为最高优先级，后端同步/安全原则继续有效。

## 历史简易测试台定位（现仅适用于 /test-console/）

原要求是给开发者一个简单可抽查的薄测试台。**负责人现明确否定将此测试台作为产品正面展示**：正式 `/console/` 需独立承载业务管理的完整列表/新建/编辑/策略/发布流程；原 `/test-console/` 只做开发调试与验收。所有安全、真实 HTTP、功能同步原则依旧适用。

## 0. 新产品化交付契约（覆盖旧最低UI要求）

1. 产品入口 `/console/`：登录、导航工作台、目录管理、流量/故障规则、版本发布、调用方、监控审计、响应式和用户帮助。**必须使用真实业务表单，不可把 JSON/HTTP 参数直接丢给非开发用户**。
2. 开发入口 `/test-console/`：旧HTTP测试/故障注入/压测说明独立保留，不再作为默认产品首页；两套页面均在Control本机静态服务，不部署新前端工程。
3. 本阶段最高优先级 `docs/design/product-console-v1.md`，对应 Codex `CODEX_PRODUCT_CONSOLE_PROMPT.md`；完整产品可用性是 Block4 综合验收之前的硬门槛。
4. 若现有管理 API 未支持查询策略绑定等产品必要的只读能力，允许最小新增正式 GET 接口并有RBAC/测试；不能伪造状态或添加不受控写操作。

## 1. 旧测试台的目的和定位

旧测试台 `/test-console/` 是**本机操作与验证后端业务的薄页面**，不是正式产品；新产品的职责见第0节。负责把本地已经完成的功能以可点击、可输入、可观察真实 HTTP 结果的形式展示给负责人，以便在最小可执行 Demo 完成后集中手动测试，在后续开发中按需单独测试。

**强制规则：每完成一个功能块，后端、前端、定向测试、阶段记录必须同步更新；不能出现“后端已做、网页没有入口、进度却显示完成”的情况。**

## 2. 技术约束

1. 继续采用原生 `HTML + CSS + JavaScript ES modules`，跟随 `flowgate-control` 的 Spring MVC 静态资源一起启动；产品后台与旧测试台可以是两套静态页，不引入npm/Vite/Vue/React/Tailwind/外部CDN。
2. **正式产品**固定地址 `http://127.0.0.1:8081/console/`；**旧开发工具** `http://127.0.0.1:8081/test-console/`，仅回环绑定，不宣称可公网部署。
3. 网页只作为 HTTP 客户端，不复制业务判断、不自行判定限流/熔断成功；展示实际 `status`、返回 JSON/文本、请求耗时、Request ID、操作错误和版本状态。
4. 管理请求走同源 `/admin/**`；Gateway 数据请求走 `http://127.0.0.1:8080`，CORS 只允许明确本地 Origin。不在前端调用 `/internal/**` 或保存内部 Key。
5. 管理员 Token、Caller Token 只存 JS 内存，刷新页面清空；密码和凭证不写 localStorage、cookie、console、URL Query、静态文件。对响应中的一次性 Token 仅在必要的用户可见区域短暂展示，有清空按钮。
6. 未实现或依赖未就绪的按钮必须**禁用并说明原因**，绝不能硬编码示例成功响应假装后端已完成。

## 3. 渐进展示范围

| 阶段 | 保留上一阶段所有真实测试能力 | 本阶段网页必须新增 |
|---|---|---|
| Block 1 | Block 0：fast GET、echo POST、slow GET、Trace ID 与状态码/health | 登录/角色、服务/API/路由/策略草稿、Caller、版本发布/回滚、节点版本、审计 |
| Block 2 | Block 0+1 已实现所有操作 | 限流配置及拒绝结果、并发许可、热点隔离的最小测试入口/结果，标明真正执行与未执行 |
| Block 3 | Block 0+1+2 已实现所有操作 | 超时、熔断、降级与恢复、控制面/Redis 故障模式、指标展示及可控测试入口 |
| Block4产品化 | 旧 `/test-console/` 全部真实能力保留 | **新 `/console/` 产品后台全日常任务：列表/新建/编辑/策略/发布/调用方/监控**；不以开发测试台代替产品 |
| 最终验收 | 所有已实现操作 | 产品台真人体验 + 旧测试台脚本入口，三种压测模式的结果**链接/说明**；不要求浏览器承担压测 |

页面模块允许增加卡片、Tab、折叠面板，但不得为视觉效果新增重依赖。功能多时优先拆分一个小 JS 辅助文件，保持清晰中文注释。

## 4. 每次 Codex 任务完成时的强制检查

1. 先实现并通过当前后端业务的定向测试，再为本轮可操作能力新增网页输入、动作、实际反馈；确保不是仅在文档列出功能。
2. 已完成的旧功能不能从网页删除或退化；接口改名时同时改网页调用，防止后端/前端契约漂移。
3. 新功能未就绪显示“未实现”或“依赖不可用”，区分“本地探测失败”和“业务拒绝”；保留 HTTP 实际结果。
4. 至少测试：静态页面访问 200、主要按钮调用目标路径、正常与一个错误响应渲染；安全检查静态源文件无 Token、密码或内部密钥。
5. 更新网页的“功能完成状态表”、对应 `docs/progress/` 阶段文件和 README 项目当前状态；记录命令、结果及截图（如有）但不伪造运行证据。
6. 所有网页功能和后端同步提交到同一功能块分支；不提前实现下一阶段功能，不推送/合并 main。

## 5. 用户手动测试的触发时机

负责人明确要求：**最小可执行 Demo 完成后再进行第一次集中人工测试**。开发中 Codex 仍需正常执行本块自动化定向测试和最小端到端验证，不得把“暂不人工测试”理解为“不运行测试”。形成 Demo 后提供一页中文使用说明，包含环境依赖、启动命令、测试台 URL、推荐点击路径、预期状态码、已知限制。人工发现的问题仍在所属功能块修复并回归。
