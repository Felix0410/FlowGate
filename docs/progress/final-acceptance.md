## 1. 验收范围

全量 B01—B13 主线，包括网关代理、服务和 API 管理、管理员及调用方身份、配置发布/回滚、Redis 分布式速率治理、本机并发保护、热点隔离、超时/熔断/降级、监控、审计、节点恢复。E01—E03 仍非强制验收，不补造无需求的技术栈。

重点是给出**可复现、可解释、包含失败和成本数据**的证明，而不是追求某个未经证实的漂亮吞吐数字。

## 3. 完整性能实验设计（不要由 Codex 临时改变口径）

必须进行三组实验并保存负载配置：

1. **直连下游**：客户端不经过 Gateway，直接请求 Demo。
2. **经 Gateway、不启动治理**：测纯代理的延迟、吞吐、CPU/内存开销。
3. **经 Gateway、启用治理**：同样入口、相同负载、相同下游资源，观察拒绝率、普通 API 性能及保护效果。

三组必须说明：硬件/操作系统/JDK、服务实例数、网络、Redis/MySQL 运行位置、Demo 工作线程或共享资源容量、压测工具及版本、请求到达模型、并发/请求速率、预热/持续时间、指标采样窗口。优先复用本机已有的 k6、JMeter 或 wrk 中**一种**即可，不为了压测引入新运行时中间件；若没有工具，选择一个简单易安装的负载工具并说明原因。

**指标至少包括**：总请求、有效成功吞吐 RPS、429、503、5xx、超时数、P50/P95/P99、CPU、内存、下游在途请求或负载、Redis 成本。不能用“总响应数”混淆“有效业务成功吞吐”；拒绝流量需要单独统计。

**热点隔离实验**：
- 普通快速查询与慢/热点业务确实竞争同一个明确的受限资源。
- 在同样的热点负载下，关闭治理先测普通 API 尾延迟，再发布服务/路由预算与并发限制重复运行。
- 输出普通查询 P95/P99、成功吞吐、热点 429/503、资源变化和网关开销。若普通接口无改善，必须分析原因并保留失败证据，不能捏造收益或宣称“完全隔离”。
- 一台与两台 Gateway 分别测试，明确 Redis 速率限额跨节点共享、本机并发限额随实例数变化的局限；不把本机 Semaphore 说成全局容量约束。

## 4. 统一故障注入

1. 关闭 Control，确认 Gateway 继续使用最后的合法快照但不能取得新规则；重新打开后周期追平。
2. 短暂关闭 Redis，验证非公开 API 的认证 fail-closed；受限业务按已定义模式返回 503 或经过显式配置的保守降级；恢复后功能正常。
3. 让 Demo 返回大量 500/长延迟，观察熔断打开、短路、半开探测和恢复；检查请求无无界队列。
4. 两管理员并发发布同一 expectedVersion，确认数据库 CAS 冲突和审计一致。
5. 发送伪造 X-Request-Id、X-User-Id、Forwarded/XFF Header 和未授权 URI，确认不能越过可信代理边界或借路由访问控制面。
6. 压力下客户端提前断开，验证并发许可无负值、未释放泄漏或重复释放。

## 5. 验收标准与问题闭环

- 全量编译、回归和关键端到端用例真实通过；若未通过逐条记录，不将“未运行”当“通过”。
- 实测性能和可靠性结果有脚本、原始数据、环境说明和可复现步骤。性能目标采取“呈现收益和成本”而非事先虚构 RPS/P99 数值。
- 发现问题先在对应实现模块修复，并运行直接受影响的定向测试，然后重新运行必要的整体验收，确保大测试不被老问题污染。
- 代码没有增加无业务必要的新中间件；核心逻辑有准确中文注释，长逻辑 1/2/3 分点；仓库仍没有黑马点评原商户/秒杀/订单业务的核心交付链路。
- 所有阶段进度文件内的分支、Commit、完成状态、已通过与未通过测试必须与 Git 事实一致。最终由负责人和 ChatGPT 确认项目是否交付。

## 6. 本地 Codex 输出格式

交付：1）全量构建命令及输出摘要；2）测试矩阵通过/失败/未执行；3）三组压测脚本、环境与原始数据路径；4）故障注入记录；5）主要问题修复及关联 SHA；6）当前项目已实现能力与尚未完成清单；7）文档/中文注释/技术必要性检查结果。

本块允许按需求创建**真实测试脚本和原始结果文件**，但不新增多份重复规划文档。将最终简要结论写回本文件，必要证据引用仓库中的脚本与日志，较大测试输出可保存在 GitHub 附件或用户指定位置，不把敏感日志/凭证提交公开仓库。
